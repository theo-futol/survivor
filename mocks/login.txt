CartePro — test accounts, one per role
=========================================

Created by seed-roles.sql (this folder). Local development only — these
credentials are public, never reuse them anywhere real.

  Role      Email                       Password
  --------  --------------------------  ---------------
  ADMIN     admin@cartepro.test       AdminPass1!
  COMPANY   company@cartepro.test     CompanyPass1!
  PARTNER   partner@cartepro.test     PartnerPass1!
  EMPLOYEE  employee@cartepro.test    EmployeePass1!

Passwords are stored SHA-256 hashed, matching hashPassword() in
CartePro/lib/services/auth_service.ts.


What each account is attached to
--------------------------------

  ADMIN     no company (companyId is NULL) — bypasses every ownership check
  COMPANY   Employeur Test SA (c0000000-0000-4000-8000-000000000001, isPartner = false)
  EMPLOYEE  Employeur Test SA — same employer, balance 5000
  PARTNER   Le Comptoir du Midi (a0f9dfc0-b6d4-4001-8880-c12c01b44f24, isPartner = true)

All four are seeded with accountStatus = ACCEPTED. Login answers 403 ("Compte
non validé") for any account that is not ACCEPTED, so the 50 employees in
seed.sql — seeded with a random mix of ACCEPTED, PENDING and REFUSED — cannot
all log in; that is deliberate, not a bug.

The COMPANY and EMPLOYEE accounts share an employer, so the employer-scoped
endpoints (GET /api/v1/salaries, the abondement route) return data instead of an
empty list. seed.sql has its own 12 employer companies (isPartner = false), but
they are shared out among the 50 seeded salariés, so seed-roles.sql adds
"Employeur Test SA" as a dedicated one.


What seed.sql brings on its own
-------------------------------

  50 salariés    <prenom>.<nom><n>@example.fr (e.g. lucas.martin0@example.fr),
                 password Secret123!, each attached to one of the 12 employer
                 companies through "companyId" (round-robin).
  18 gérants     one login per company — PARTNER for the 6 partenaires, COMPANY
                 for the 12 employeurs — gerant@<nom-de-la-societe>.fr, same
                 password Secret123!, all ACCEPTED. Logging in as one of these
                 is the quickest way to see the employer-scoped endpoints return
                 real data.
  3 agents       2 agents + 1 admin (ADMIN): agent1.seed@cartepro.fr,
                 agent2.seed@cartepro.fr, admin.seed@cartepro.fr / Admin1234!

Fixtures worth knowing about, all generated:

  - the salariés refused at signup carry a userRefusalReason row written by one
    of the two agents;
  - 2 salariés are in bannedUser, so GET /api/v1/salaries reports isBanned;
  - 3 salariés are deactivated ("expiredAt" set) and only show up with
    ?includeInactive=true;
  - the last 2 employer companies are closed (company.active = FALSE);
  - qrCode is deliberately left empty: a code lives 300 s, so any seeded row
    would already be expired. Call POST /api/v1/qrcode to get a live one.


Loading them
------------

  docker compose --env-file .env.development up -d db
  docker exec -i cartepro_db psql -U postgres -d cartepro < mocks/seed.sql
  docker exec -i cartepro_db psql -U postgres -d cartepro < mocks/seed-roles.sql

seed-roles.sql must run after seed.sql (it reuses companyValidationReason id 1,
companyCategory id 1 and the seeded partner company). Re-running it is safe —
every insert is ON CONFLICT DO NOTHING.


Getting a token
---------------

  curl -sk -X POST https://localhost:3000/api/v1/login \
    -H 'Content-Type: application/json' \
    -d '{"email":"admin@cartepro.test","password":"AdminPass1!"}'

The response carries { token, expiresIn, user }. Pass it on every other call:

  -H "Authorization: Bearer <token>"
